## 终端与 Shell

终端和 Shell 是两样东西。终端负责显示字符、接收按键；Shell 是跑在终端里的一个普通程序，负责解释你输入的那一行。你在屏幕上看到的文字，是终端把收到的字节画出来；你敲下的按键，是终端把它们交给 Shell。

终端的历史比图形界面长得多。最早的终端是 ASR-33 这样的电传打字机，一台机器上接着一条线，线的末端就是计算机。Teletypewriter 被缩写成 TTY，所以今天终端设备还叫 `tty`，`tty` 命令会打印当前终端的设备路径。VT100 是另一条支线：它不再靠机械打字，而是用一组控制序列来移动光标、改变颜色。今天的终端模拟器仍然解释同一套序列，`$TERM` 告诉程序自己模拟的是哪一台，terminfo 数据库描述这台终端支持哪些能力。

Shell 的工作是一个循环：打印提示符，读入一行，切词、展开、找到程序、启动它、等它结束、记下返回码，然后回到提示符。提示符通常由 `$PS1` 决定，默认形态是 `user@host:cwd$`，其中 `$` 表示你不是 root。

命令行最终交给程序的是一个字符串数组，习惯上叫 `argv`。执行 `echo hello` 时，Shell 找到 `echo` 这个程序，把 `argv[0]` 设为 `echo`、`argv[1]` 设为 `hello`，剩下的解释工作归程序自己。Shell 并不理解 `hello` 是什么意思，它只负责把词切开。

## 一条命令的旅程

一行命令从回车到执行，要经过好几步。第一步是切词：空格和制表符把行拆成词，连续空白算一个分隔符。第二步处理引号。单引号里的内容完全字面，连 `$` 都不展开；双引号保留变量和命令替换，但阻止切词；反斜杠转义后面那一个字符；`$'...'` 是 ANSI-C 写法，可以写 `\n`、`\t` 这样的转义序列。

引号处理完，变量才开始展开。`$HOME`、`${HOME}` 都是取值，花括号用来划清变量名的边界，`${HOME}dir` 不会去找一个叫 `HOMEdir` 的变量。`export` 把变量放进环境，子进程才能继承；没有 `export` 的变量只属于当前 Shell。命令替换 `$(...)` 会先执行里面的命令，用它的标准输出替换当前位置，末尾的换行会被去掉。

展开的结果还会再次切词。`files="a b"; rm $files` 会删掉两个文件，因为展开后的空格又变成了分隔符；写成 `rm "$files"` 才是一个参数。这是 Shell 里最常见的一类 bug。

接下来是文件名展开，也就是 glob。`*` 匹配任意长度的字符，`?` 匹配一个字符，`[]` 匹配字符集合，`**` 在开启 globstar 后递归匹配。glob 不匹配以点开头的隐藏文件，`.` 和 `..` 也不参与。没有文件匹配时，bash 默认把模式原样保留，程序真的会收到一个叫 `*.py` 的参数；`nullglob` 会把它变成空，`failglob` 则直接报错。花括号展开 `{a,b}` 发生在 glob 之前，它纯粹是文本替换，不需要文件存在。

词都准备好了，Shell 沿着 `$PATH` 找程序。`$PATH` 是用冒号分隔的目录列表，从左到右查找，第一个命中的生效，所以路径顺序就是优先级。`which -a` 和 `type -a` 能看到所有候选；`type -a` 还会告诉你某个名字是别名、函数、内建命令还是外部程序。找到之后，Shell 先 `fork` 出子进程，子进程再 `exec` 成目标程序，父进程用 `wait` 等它结束。内建命令不走这条路：`cd`、`export`、`umask` 必须由 Shell 自己执行，因为子进程改不了父进程的工作目录和环境。

## 打开终端后发生了什么

打开终端时，终端模拟器向内核申请一对伪终端：master 和 slave。Shell 的 stdin、stdout、stderr 都接在 slave 上，模拟器则从 master 读数据、画到窗口里。两边之间还有一层行规程，负责回显、行编辑和把控制键翻译成信号。

每个进程默认有三个文件描述符：0 是标准输入，1 是标准输出，2 是标准错误。把它们都当文件看是 Unix 的基本设定，所以 `ls /proc/$$/fd` 能看到当前 Shell 的 fd 指向哪个设备。macOS 没有 `/proc`，可以用 `lsof -p $$`。

按键的路径是这样的：模拟器把按键写成字节送到 master，行规程按规范模式处理。普通字符进入缓冲区并回显；退格删除一个字符；回车把整行交给 Shell；缓冲区为空时按 `Ctrl-D` 表示 EOF；`Ctrl-C` 让内核给前台进程组发 `SIGINT`；`Ctrl-Z` 发 `SIGTSTP`，把作业挂起；`Ctrl-\` 发 `SIGQUIT`。这些键本身不会变成字符传给程序，除非终端处在 raw 模式。

`vim`、`less`、`tmux` 这类全屏程序会自己把终端切到 raw 模式，按键直接交给程序，光标移动和重绘全靠转义序列。`stty -a` 能查看当前终端的模式，`stty raw` 和 `stty sane` 用来切换和恢复。

关掉终端窗口时，内核给这个会话里的进程发 `SIGHUP`。这就是为什么后台任务会跟着终端一起死。`nohup` 让程序忽略 `SIGHUP`，`disown` 把已经启动的作业从 Shell 的作业表里摘掉，`tmux` 则干脆让进程跑在另一个不随窗口关闭的会话里。

## 重定向和管道

重定向的本质是改文件描述符的指向。Shell 先打开目标文件，再把 fd 1 指过去，程序对此一无所知。`>` 截断写入，`>>` 追加，`<` 换掉标准输入，`2>` 改标准错误，`&>` 同时改 1 和 2，`/dev/null` 是一个丢弃写入的设备。开了 `noclobber` 之后 `>` 不覆盖已存在的文件，`>|` 可以强行覆盖。

`2>&1` 的顺序经常被写错。`cmd > out 2>&1` 先把 stdout 指向 `out`，再把 stderr 指向 stdout 当前的位置，两个流都进文件；`cmd 2>&1 > out` 先把 stderr 指向终端，再把 stdout 指向文件，错误仍然打在屏幕上。重定向从左到右生效，顺序就是语义。

`exec` 可以把重定向变成持久的：`exec 3> log` 打开 fd 3，之后 `echo hi >&3` 都写进这个文件；`exec > log` 则把整个脚本后续的输出都改道。`sudo` 和重定向放在一起也容易踩坑：`sudo echo x > /root/f` 里，打开文件的是当前 Shell，不是 `sudo`，所以权限检查按当前用户算。正确写法是 `echo x | sudo tee /root/f`。

管道把前一个程序的标准输出接到后一个程序的标准输入。管道两端同时运行，内核在中间维护一个缓冲区。写端写满就阻塞，读端读空就等待，这种反压让生产者和消费者自然同步。所有写端关闭后，读端读到 EOF；读端提前退出时，写端会收到 `SIGPIPE`，进程以 141 结束。`set -o pipefail` 让管道的返回码取第一个失败的命令，`PIPESTATUS` 数组则保留每一段的状态。

缓冲会让管道的行为看起来很奇怪。stdout 接终端时通常是行缓冲，接管道时变成块缓冲，于是 `tail -f app.log | grep error` 可能半天没有输出。`stdbuf -oL`、`grep --line-buffered` 或 `unbuffer` 可以强制行缓冲。`tee` 则把标准输入同时写到标准输出和文件，适合既想留日志又想看屏幕的场景。

## bash 编程与脚本

Shell 本身是一门编程语言。每条命令都有返回码，0 表示成功，非 0 表示失败，`$?` 保存上一条命令的返回码。`&&` 和 `||` 根据返回码短路，所以 `mkdir /tmp/x && cd /tmp/x` 只在建目录成功后才切换。`if` 和 `while` 判断的也是返回码，不是布尔值。

`test` 是最常用的条件命令，`[` 是它的另一种写法，所以 `[ -f file ]` 里方括号两边必须有空格。bash 另外提供了 `[[ ]]`，它支持 `&&`、`||` 和 `=~` 正则匹配，也不会因为变量为空而把语法拆坏，写 bash 脚本时优先用它。字符串比较用 `=`，数值比较用 `-eq`、`-lt` 这些，混用会得到意料之外的结果。

位置参数是脚本的入参：`$0` 是脚本名，`$1` 到 `$9` 是前九个参数，`$#` 是数量，`$@` 是全部参数。`"$@"` 展开成多个独立的词，保留每个参数里的空格；不加引号的 `$@` 会被再次切词。

脚本的第一行通常是 shebang：`#!/usr/bin/env bash` 告诉内核用哪个解释器执行这个文件，`/usr/bin/env` 会去 `$PATH` 里找 `bash`。脚本需要可执行位才能直接运行，`chmod +x script.sh` 之后 `./script.sh` 才有效；不加 `./` 而直接写 `script.sh`，Shell 会去 `$PATH` 里找，当前目录通常不在其中。

`set -euo pipefail` 是脚本的常用开头：`-e` 让任意命令失败时退出，`-u` 让引用未定义变量时退出，`-o pipefail` 让管道里任何一段失败都算失败。`set -x` 打印每条命令展开后的样子，是排错的第一手段。

后台任务用 `&` 启动，`$!` 拿到它的 PID，`kill` 用来结束它。一个典型的脚本是这样反复跑测试直到失败：

```bash
#!/usr/bin/env bash
set -euo pipefail

while cargo test my_test > run.log 2>&1; do
  echo "passed"
done

tail -n 20 run.log
```

写复杂脚本时，`shellcheck` 能指出大部分引号和返回码问题。

## 常用文本工具

`man` 是命令的说明书，`--help` 给出简短版本，`tldr` 只列最常见的几个例子。查看文件用 `cat`，长文件用 `less`，`head` 和 `tail` 各看一头一尾，`tail -f` 持续跟踪追加内容。

`sort` 排序，`uniq` 去掉相邻重复行，所以统计频次总是 `sort | uniq -c`。`grep` 按正则找行，`-r` 递归目录，`-l` 只列文件名。`sed` 做流式替换，`sed -i 's/old/new/g' file` 就地改写。`find` 按路径、类型、时间、大小筛文件，`-exec` 对每个结果执行命令。`awk` 按列处理文本，`awk '{print $2}'` 取第二列，`-F,` 换分隔符。

把它们串起来就是一条真实的数据管道。比如统计某台机器上 SSH 断开连接最多的用户名：

```bash
ssh myserver 'journalctl -u sshd -b-1 | grep "Disconnected from"' \
  | sed -E 's/.*Disconnected from .* user (.*) [^ ]+ port.*/\1/' \
  | sort | uniq -c | sort -nr | head -n 10
```

远端负责取日志和过滤，本地负责抽取、排序和计数，每一段都很小，组合起来却很能干。

## 容易混淆的问题

**`$SHELL` 与 `$0`** 不是一回事。`$SHELL` 是登录时用的 Shell，来自账号配置；`$0` 是当前这个 Shell 进程的名字。想看真实进程，用 `ps -p $$`。

**`$TERM` 与终端能力**。`$TERM` 只是一个名字，比如 `xterm-256color`，真正的能力表在 terminfo 里。名字写错，程序要么不敢用颜色，要么输出一堆乱码。

**终端里跑非 Shell 程序**。`vim`、`python`、`less` 都是普通进程，只是它们关闭了行规程的回显和行编辑，自己处理按键，退出时再把终端恢复原状。

**没有终端的环境**。脚本、CI、`ssh host cmd` 里没有 tty，`isatty` 为假，行缓冲变成块缓冲，需要交互的程序会直接失败。`ssh -t` 可以强制分配一个伪终端。

**`Ctrl-C` 的完整链路**。按键先到终端驱动，驱动给前台进程组发 `SIGINT`，进程自己决定退出还是捕获。Shell 只负责作业控制，并不亲手发这个信号。

**`if` 与 `[`**。`[` 是一条命令，不是语法，所以方括号两侧要有空格，末尾要有 `]`。`[[ ]]` 是 bash 的语法结构，规则不同。

**`$?` 与 `$!`**。`$?` 是上一条命令的返回码，`$!` 是最后一个后台进程的 PID。

**`./script.sh` 与 `PATH`**。当前目录默认不在 `PATH` 里，直接写 `script.sh` 会找不到；`./script.sh` 明确指定路径，再配合 shebang 和可执行位才能运行。
